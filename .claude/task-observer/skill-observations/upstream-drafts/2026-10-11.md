## Issue 1 — Bundle-Prüfung vs. {{…}} (Beobachtung #6)

paste into Title
````
Pre-delivery gate: the unresolved-slot rule has no waiver a JSON (or other non-HTML) file can use
````

paste into Description
````
**What happened.** A scheduled review staged a one-paragraph additive change to a third-party skill whose `examples/` folder holds automation blueprints in JSON. `validate-skill-bundle.py --pack` failed with `unresolved template slot ('{{now}}')` in three of those JSON files. `{{…}}` is that platform's mapping syntax, so the hits are real content, not edit residue.

**Why the current text did not prevent it.** The two documented waivers (weekly-review.md, "Delivering updated skills", gate item 7; `slots_are_intentional()` in the validator) are a path containing `template`, or a first line reading `<!-- template: slots intentional -->`. Neither fits: the files are not templates, and JSON cannot carry an HTML comment. Hand-packing is ruled out by the same section, so the run had no compliant way to produce the bundle and delivered the staged directory only.

**Suggested fix.** A waiver that works for every file type, e.g. a `.slots-intentional` file in the skill root listing globs (`examples/*.json`), read by `slots_are_intentional()` and documented next to the two existing waivers. Every other residue rule keeps running on those files.

**Principle.** A content heuristic in a delivery gate needs an opt-out usable by every file type the gate scans; a waiver written in one format's comment syntax leaves the others a choice between a false failure and a bypass.

Checked against upstream HEAD 56e8907: local `scripts/validate-skill-bundle.py` and `references/weekly-review.md` are byte-identical (`cmp`). Adjacent: #105 (the `\1` residue rule that introduced the gate item) — this report is about the slot rule's waiver only.
````

## Issue 2 — Prompt für geplante Cloud-Läufe (Beobachtung #7)

paste into Title
````
Scheduled-prompt rules: a cloud run may start with no checkout, and tools must be named by their exact identifier
````

paste into Description
````
**What happened.** The weekly review was registered as a cloud routine that starts a fresh session per firing. Firing 1: the session had no repository checked out, so the pinned workspace path did not exist and the run stopped at the probe. The prompt was changed to attach and clone the repository first. Firing 2: the prompt said "call the `add_repo` tool"; the session searched for that bare name, found nothing (the real tool name carries a server prefix), and stopped as instructed. Both were caught only by the existing rule that setup is not done until one firing has reached the workspace from inside the task's own execution context (from #121) — an interactive test of the same prompt would have passed both times.

**Why the current text did not prevent it.** environments.md ("A scheduled-task prompt's first listed action is its first tool call", "The second listed action leaves a started marker", "The access grant is part of the task definition") assumes the workspace exists at fire time and only its access may be missing. It says nothing about a run whose filesystem starts empty, or about how a prompt should name a tool.

**Suggested fix.** Two lines in that block: (1) a scheduled run may start with no checkout at all — where the workspace lives in a repository, the prompt's first action obtains it (clone/attach), with a stated fallback, and the probe follows; (2) every tool a scheduled prompt names is named exactly as the target session lists it (full prefixed identifier), never a short form.

**Principle.** A prompt for an unattended run is read literally by a session with a different tool list and filesystem: name tools by their exact identifiers, give every acquisition step a fallback, and prove the setup with a real firing.

Checked against upstream HEAD 56e8907: local `references/environments.md` is byte-identical (`cmp`). Adjacent: #121 (denied workspace, access grant) and #151 (run stops after its first call) — this report covers the absent checkout and tool naming, which neither does.
````

## Issue 3 — Workspace-Pfad auf einem zweiten Rechner (Beobachtung #8)

paste into Title
````
Anchoring: a workspace committed inside a repository has a different absolute path on every machine that checks it out
````

paste into Description
````
**What happened.** The workspace lives inside a version-controlled repository so that cloud sessions and a local machine share one log. The activation block pins it, and both helper commands, as the cloud container's absolute path (`/home/user/<repo>/…`). On the local Windows checkout the same workspace sits under `C:\Users\<name>\<repo>\…`. The session there had to translate the path by hand; a literal run of the pinned command would have hit the missing-directory guard, and a hand-adapted snippet with a relative path is exactly the case SKILL.md warns reports an empty, clean backlog.

**Why the current text did not prevent it.** environments.md, "Anchoring the workspace", defines the anchor as one stable absolute path and covers ephemeral checkouts, per-project shards and (via #261) storage that is not always mounted. It does not cover the legitimate case of one workspace that travels with a repository checked out on several machines: there every machine has a correct but different absolute path, and a single pinned string is right on one of them only.

**Suggested fix.** In "Anchoring the workspace", add the repository case: pin the workspace relative to the repository root, resolved once per session (e.g. `git rev-parse --show-toplevel`), and derive the absolute path from it; or, where the activation block must hold literal paths, list one per known machine. Note that the helper scripts already take the root as an argument, so only the activation text needs the per-machine form.

**Principle.** "Absolute" protects against a wrong working directory, not against a second machine: when the workspace lives inside a versioned repository, the stable anchor is the repository root, and the absolute path is derived from it on each machine rather than written down once.

Checked against upstream HEAD 56e8907: local `references/environments.md` and `SKILL.md` are byte-identical (`cmp`). Adjacent: #261 (always-mounted, user-owned storage) and #273 (a forked instruction file with a different pinned path) — this report is about one repository-borne workspace on several machines.
````
